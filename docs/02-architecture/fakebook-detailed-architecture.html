Architecture · Authorization · Data flow

Fakebook, request to persistence

Three source-grounded views explain how the React client authenticates, how the gateway and services enforce identity, how synchronous service calls are relayed, and how durable data and asynchronous events move through the system.

01 · Sequence

Authentication and an authorized API request

Keycloak issues the JWT; the frontend refreshes and attaches it; the gateway validates and routes it; the target service validates it again and applies endpoint and ownership rules.

02 · Dependency graph

Synchronous gateway and service-to-service calls

The gateway can route to every business service. OpenFeign calls carry the current user JWT where configured; Feed can obtain an internal client-credentials token when no user token exists.

03 · Data flow

Events, database ownership, and Redis caching

Each service persists its own schema. User Service uses Redis for profile and social-list read caches. Kafka carries projections, cleanup, and realtime signals without making the broker a source of truth.

Authorization checkpoints

  • Frontend refreshes the token before API calls.
  • Gateway validates issuer, audience, and authorities.
  • Services validate JWTs again and use sub for user identity.

Sync interaction

Gateway discovery routes use /services/{serviceId}/**. Feign calls cover friendship checks, post lookup, feed hydration/backfill, and media validation.

Data rule

Each service owns its MariaDB schema. Redis accelerates selected User Service reads; cache failure does not replace the database as source of truth.

Source scope: current Fakebook frontend, gateway security/routing, downstream SecurityConfiguration classes, Feign clients, Kafka bindings, cache configuration, and persistence mappings.
